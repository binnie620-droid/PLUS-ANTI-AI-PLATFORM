# industry-screen UX/유니버스 재설계

날짜: 2026-08-13
브랜치: `industry`
대상: `.claude/skills/industry-screen/SKILL.md` (Skill 1/1.5, 담당 B)

## 배경 — 세 가지 문제 제기

1. **UX**: `DART_API_KEY`/`FRED_API_KEY`가 없으면 그냥 조용히 건너뛰고 진행했다. 사용자가
   키를 넣을 기회 자체가 없었다.
2. **유니버스 편향**: `data/industry_universe.csv`가 사람이 손으로 고른 고정 6개 산업
   (조선·조선기자재, 방산·항공, 전력기기·중전기, 시멘트·건자재, 환경·폐기물·수처리,
   원자력·발전정비)이었다. 전부 "설비·물질 기반 중공업"에 쏠려 있어, discover를 돌려도
   항상 비슷한 결과만 나온다. 서비스업·컨설팅·금융 등 Q1-YES **함정(☠) 후보가 나올 여지가
   구조적으로 없었다** — README가 "함정 후보를 버리지 마라"고 강조하는데 애초에 후보 풀에
   함정이 존재할 수 없는 설계였다.
3. **일반 UX 친절도 부족**: 내부 용어(Q1~Q5, G1, coverage_count)가 그대로 노출되고, 진행
   상황이 안 보이고, 산업 판정 후 다음 스킬(기업 판정)로 이어지는 흐름이 끊겨 있었다.

## 조사 결과 (설계에 영향을 준 사실들)

- **FnSpace(FnGuide) MCP는 종목코드 하나를 주면 그 종목의 재무/목표주가/추정실적을
  반환하는 6개 도구뿐** — "산업별 종목 목록"이나 "전체 산업 리스트"를 조회하는 기능이
  없다. FnGuide API 자체로는 유니버스(산업→종목 매핑)를 만들 수 없다.
- FnSpace 유료 구독은 **2026-08-15 만료**. 그 이후 `get_financials` 등 유료 도구가
  멈출 수 있음 (무료인 `list_items`만 계속 동작).
- **DART에도 "업종코드로 회사 목록 일괄 검색" 기능이 없다.** 회사별 `induty_code`는
  `company.json`을 회사 하나하나 호출해야 알 수 있다. 즉 "매번 완전 실시간으로 전체
  상장사(~2500개)를 업종별로 묶기"는 사실상 불가능 — 매번 수천 회 호출이 필요하다.
- `data/consensus.csv`는 README 계약상 A(개발) 소유 — `adapters/consensus.py`가
  FnGuide를 정규화해서 만든다. B(이 스킬)가 소유한 건 `industry_universe.csv`뿐이었다.

## 목표

- API 키가 없을 때 채팅으로 명시적으로 물어보고, 받으면 저장한다.
- 고정된 산업 유니버스를 없애고, 실행할수록 유기적으로 커지는 캐시로 대체한다.
- discover가 테마와 무관하게 항상 같은 업종만 내놓는 구조적 편향을 없앤다.
- 흐름이 끊기지 않게: 사용자에게 묻는 지점을 최소화하고, 진행 상황은 텍스트로만 보여준다.
- 데스크 파이프라인(산업→기업→검증→팀장)으로 자연스럽게 이어지는 마무리를 항상 붙인다.

## 비목표 (Out of scope)

- `company-screen`(C), `pro_tackler`(D), `desk-head` 스킬 자체의 로직 변경 — 이 설계는
  이들과의 **연결 지점(다음 단계 유도 질문)만** 다룬다.
- `adapters/consensus.py`, `data/consensus.csv` 스키마 변경 — A 소유 계약, 손대지 않는다.
- `01-industry.json`의 필드명/스키마 변경 — `contracts/pipeline.md` 계약 그대로 유지.

## 설계

### 1. 전체 흐름

```
0. 키 점검        DART_API_KEY / FRED_API_KEY 확인
                   → 없으면 채팅으로 물어봄 → 받으면 로컬 .env에 저장
                   → 못 받으면 이유를 설명하고 즉시 abort (JSON을 만들지 않는다)
1. 모드 확인       (기존 Step 0 그대로) 산업 미지정 시 discover/verify 질문
2. [discover만]    "AI 고도화" 테마로 업종을 가리지 않고 폭넓게 후보 브레인스토밍
                   → 확인 질문 없이 바로 진행, 스캔 중 진행상황을 1줄씩 출력
3. 유니버스 구축    data/industry_cache.json 확인 → 캐시에 없는 업종/티커만
                   DART로 조회해 캐시에 추가 (자동 캐싱, 사람이 손으로 안 채움)
4. 컨센서스 조회    FnSpace로 티커별 실시간 컨센서스 직접 조회 (진행상황 계속 출력)
5. Gate Logic      기존 G1~sweet-spot 로직 그대로 (변경 없음)
6. 결과 출력        01-industry.json 저장 + 채팅 요약 (내부 용어는 쉬운 말 병기)
7. 다음 단계 유도    "이 중 하나로 Skill 2(기업 판정)로 넘길까요?"로 항상 마무리
```

**사용자에게 묻는 지점은 2곳뿐**: ① 키가 없을 때, ② 결과를 낸 뒤 다음 단계 유도.
discover의 스캔 규모에 대한 사전 확인은 넣지 않는다 — 진행상황 텍스트로 대체한다.

### 2. Step 0 — API 키 온보딩

- 스킬 시작 시 `DART_API_KEY`, `FRED_API_KEY` 존재 여부를 함께 확인한다 (환경변수 →
  없으면 프로젝트 루트 `.env` 순으로 확인).
- 하나라도 없으면 **한 번에** 채팅으로 요청한다. 예:
  ```
  "이 스킬은 DART_API_KEY와 FRED_API_KEY가 필요합니다. 채팅에 바로 붙여넣어 주세요.
   - DART: https://opendart.fss.or.kr 에서 발급
   - FRED: https://fred.stlouisfed.org/docs/api/api_key.html 에서 발급
   (다음부터 다시 안 묻도록 로컬 .env에 저장합니다)"
  ```
- 사용자가 값을 주면 `.env`(gitignore 대상)에 `KEY=value` 형식으로 저장하고 이번 세션에도
  즉시 사용한다.
- 사용자가 "없다/나중에"라고 답하면 — **둘 중 하나라도 없으면 스킬을 진행시키지 않고
  abort한다.** 부분 진행이나 저하된 모드로 계속하지 않는다. abort 메시지에 어떤 키가
  없어서 멈췄는지 명시한다.
- `.env`가 이미 존재하고 값이 있으면 이 단계는 조용히 통과 (매번 묻지 않음).

### 3. 유니버스 구축 — 캐시 + LLM 브레인스토밍 + DART/FnSpace 검증

`data/industry_universe.csv`를 없애고 `data/industry_cache.json`으로 대체한다.

**캐시 스키마 (안):**
```json
{
  "companies": {
    "009540": {
      "name": "HD한국조선해양",
      "induty_code": "31114",
      "industry_labels": ["조선·조선기자재"],
      "cached_at": "2026-08-13"
    }
  },
  "industries": {
    "조선·조선기자재": {
      "induty_codes": ["31114", "31119"],
      "tickers": ["009540", "042660", "010140"],
      "first_seen": "2026-08-13"
    }
  }
}
```

- `industries`의 키는 **데스크가 부르는 한국어 산업명**(예: "조선·조선기자재")이고,
  하나 이상의 KSIC `induty_code`를 묶은 것이다. 이 묶음은 LLM이 브레인스토밍 시점에
  판단하며, 한 번 정해지면 캐시에 기록되어 재사용된다 (매번 다시 판단하지 않음 →
  같은 산업명이 실행마다 다른 종목 집합을 가리키는 걸 방지).
- **캐시는 "허용된 산업 목록"이 아니라 "지금까지 확인된 것들의 자동 기록"이다.**
  discover/verify 어느 쪽에서든 새 업종·종목을 만나면 그 자리에서 캐시에 추가된다.
  기존 6개 산업은 삭제하지 않고 캐시의 초기 시드로 이관한다.

**discover 모드의 후보 확장 (핵심 변경):**
1. Claude가 "AI 고도화 시대 수혜/피해"라는 데스크 테마로, **업종을 가리지 않고**
   폭넓게 후보 산업을 브레인스토밍한다 — 제조업뿐 아니라 서비스·컨설팅·번역·인력파견·
   금융·유통·헬스케어 등도 포함해야 한다. 이래야 Q1-YES 함정(☠) 후보가 나올 구조적
   가능성이 생긴다 (README가 요구하는 "함정 후보 최소 1개 유지"를 실제로 만족시키려면
   후보 풀 자체에 함정이 존재해야 한다).
2. 각 후보 산업마다 Claude가 아는 대표 종목 몇 개를 지목한다 (일반 지식).
3. 캐시에 이미 있는 티커는 캐시값을 쓰고, 없는 티커만 DART `company.json`으로
   실존/업종코드를 확인해 캐시에 추가한다 (자동 캐싱, 사람 개입 없음).
4. FnSpace로 각 티커의 실시간 컨센서스를 조회해 coverage_count를 구한다.
5. 이후 로직은 기존 Gate Logic(Step 1~4)과 동일.

**검토했지만 제외한 방법:**
- *DART 최근 공시 피드로 확장*: 데이터 기반이지만 마크다운 스킬 안에서 구현이 복잡하고
  느리며, "최근 공시가 많은 회사"로 쏠리는 또 다른 편향이 생길 수 있어 제외.
- *FnGuide WICS 섹터 분류로 완전 대체*: 지금 연결된 FnSpace 도구 6개 중 섹터별 종목
  목록을 주는 기능이 없어 **도구상 불가능**함을 확인했다.

### 4. 데이터 소유권 경계 (A와의 계약)

- `data/industry_cache.json`은 B가 소유 (기존 `industry_universe.csv`와 동일한 위치의
  책임).
- `data/consensus.csv`는 그대로 두되(A의 계약 파일, 스키마 불변), **이 스킬은 이제
  FnSpace를 직접 호출해서 실시간 컨센서스를 쓴다.** consensus.csv보다 최신값일 수 있고,
  A의 파이프라인이 참조하는 값과 다를 수 있다 — 이는 알려진 리스크로 문서에 남긴다.
  (완화책이 필요하면 별도 논의: 예를 들어 이 스킬이 얻은 최신 컨센서스를 consensus.csv에
  다시 써주는 것도 고려 가능하나, 이번 설계 범위 밖으로 둔다.)

### 5. UX 디테일

- **진행 상황**: 오래 걸리는 단계(후보 산업 브레인스토밍, 업종별 DART/FnSpace 조회)마다
  "○○ 확인 중..." 형태로 짧게 1줄씩 출력한다. 최종 결과는 지금처럼 표 + 요약으로.
- **용어 친절도**: `01-industry.json`의 필드명(Q1, G1, coverage_count 등)은 계약이라
  그대로 두지만, 채팅 요약에서는 괄호로 쉬운 말을 병기한다.
  예: "G1(컨센서스 커버리지 최소 5종목 조건)".
- **파이프라인 연결**: 결과 출력 마지막에 항상 "이 중 하나를 골라 Skill 2(기업 판정,
  company-screen)로 넘길까요?"로 마무리해 산업→기업→검증→팀장 흐름을 유도한다.
  (이 스킬은 industry-screen만 수정 범위이므로, 여기서는 유도 질문만 추가하고
  company-screen 쪽 로직은 건드리지 않는다.)

## 리스크

- **FnSpace 구독 만료(2026-08-15)** — 이후 실시간 컨센서스 조회가 멈출 수 있다. 만료
  이후엔 이 설계의 4단계가 실패하므로, `consensus.csv` 폴백이 필요할 수 있음
  (이번 설계 범위 밖, 만료 이후 후속 조치로 남김).
- **LLM 브레인스토밍의 재현성** — discover를 여러 번 돌리면 후보 산업 제안이 매번 다를
  수 있다. DART/FnSpace 검증 단계가 존재 여부는 걸러주지만, "어떤 업종을 후보로
  떠올리는가"의 편차는 남는다. 캐시가 쌓일수록 편차가 줄어드는 방향으로 완화됨.
- **consensus.csv와의 값 불일치** — 위 4번 참고.
